# 案例底稿：把「PDF 抠字段 → 逐条录入网页」的人工流程自动化

> 状态：底稿（Step 12）。文中带【待确认】的均为需按客户实测填入的数字，**不得凭印象填写**。
> 适用场景：物流运单、订单、报关单、发票等「数据在 PDF / 图片里，录入目标是一套只有网页界面的老系统」。

---

## 一、一页速览

| 项目 | 内容 |
|---|---|
| 客户痛点 | 员工每天把运单 PDF 里的单号、收件人、电话、地址逐条手打进网页系统 |
| 交付形态 | 上传 PDF → 自动提取字段 → 人工校对 → 浏览器自动化录入并提交 |
| 关键技术 | pdf.js（浏览器端解析）、规则抽取、Supabase（留痕）、Playwright/CDP（填表） |
| 部署架构 | 云端接单 + 校对；录入引擎在本地 FDE 机器执行 |
| 效率变化 | 单票录入由【待确认】秒降至【待确认】秒；日单量【待确认】时，每日节省【待确认】人时 |
| 可复用性 | 换行业只改三处：字段规则、选择器映射、目标地址 |

---

## 二、现场是什么样的

这类客户的系统通常有三个共同特征，缺一个就不成立：

**其一，数据源是版式文件而非结构化数据。** 运单以 PDF 形式在邮箱、微信、供应商平台之间流转，字段位置固定但不可直接复制——复制出来会错行、丢列、中文全角半角混杂。

**其二，目标系统没有可用的接口。** 往往是多年前采购的 ERP / TMS，供应商已停止维护，或接口要另外收费、要走漫长的审批。业务部门能拿到的只有一张网页表单。

**其三，录入动作本身是机械的。** 字段固定六到八个，规则明确，但要求 "一字不差"。人做这件事的出错率与疲劳度正相关，错一单的返工成本远高于录入本身的成本。

---

## 三、为什么不用别的办法

**换系统**：采购、迁移、培训、数据迁移风险，周期以季度计。客户真正想要的不是新系统，是"别再手打"。

**要求开放接口**：技术上是正解，商务上常常走不通——供应商不配合、接口另收费、内部审批链路过长。

**纯录制式 RPA**：能解决"点网页"，解决不了"读懂 PDF"。而且录制脚本对页面改版极其脆弱，一次前端升级就全线失效。

**本方案的选择**：把问题拆成两段——"读懂文件"用解析 + 规则，"操作网页"用浏览器自动化；中间插一道**人工校对**，把机器的不确定性收敛在一个人能快速确认的界面上。

---

## 四、技术链路

| 环节 | 用什么 | 产出 |
|---|---|---|
| 1. 上传 | Next.js 页面 + 文件选择 | 原始 PDF 字节流 |
| 2. 解析 | pdf.js（Web Worker 中运行） | 纯文本，保留换行 |
| 3. 抽取 | 正则规则，逐字段匹配 | 结构化字段（运单号/收件人/电话/地址/日期/金额） |
| 4. 校对 | 可编辑表格，空值高亮"待补" | 人工确认后的字段 |
| 5. 留痕 | Supabase `documents` 表 | 原文、抽取结果、状态（extracted / reviewed） |
| 6. 录入 | Playwright 驱动浏览器，按选择器填表并提交 | 目标系统内的一条记录 + 截图存证 |

**为什么第 4 步不能省。** 解析再准也有边界：扫描件、印章遮挡、非常规版式都会让规则失效。校对界面的作用不是"让人再检查一遍"，而是把"机器不确定的地方"显式暴露出来——空值标黄、字段并排，人眼三秒能扫完。这一道工序把"自动化出错"变成"自动化提示人工补"，风险性质完全不同。

## 五、三个真实难点（这部分是本文档的核心价值）

### 难点一：PDF 在浏览器里解析，worker 版本必须与主库一致

`pdfjs-dist` 的解析放在 Web Worker 里执行，主库与 worker 必须是**同一版本、同一构建分支**。曾出现主库用 legacy 构建、worker 用标准构建，表现为页面无报错但提取结果为空。定位方法是看 Console 里的 `GlobalWorkerOptions.workerSrc` 提示，而不是怀疑正则。

### 难点二：独立 Node 脚本不会自动读 `.env.local`

Next.js 启动时会自动加载 `.env.local`，所以网页端能读到配置；但用 `tsx` 跑的独立脚本（如 `automation/run.ts`）**不会**。表现是"配置文件里明明写了，脚本却报环境变量为空"。

解法不是把配置抄进代码，而是让脚本自己加载，并且用 `import.meta.url` 反推项目根目录定位文件——否则从子目录执行时又会找不到。

### 难点三：云端跑不了浏览器

Vercel 这类 serverless 平台没有 Chromium 二进制，也缺它依赖的系统库，函数实例还是临时的。硬跑的结果是一串与业务无关的启动错误。

解法是**运行时能力探测**：同一份代码，在请求进来时问一句"这台机器具备开浏览器的条件吗"，具备就执行录入，不具备就返回一条可执行的交接指引（导出字段 JSON，回本地执行）。这样云端与本地共用一套代码，而不是维护两个分支。

## 六、效率测算模型

不要凭感觉说"提效 80%"，先算。

**符号定义**

- `N`：日均单据量（【待确认】）
- `T_manual`：人工单票耗时，含查找、复制、粘贴、核对（【待确认】，行业常见区间 60–180 秒）
- `T_auto = T_parse + T_review + T_entry`：解析约 2 秒、校对约 15 秒、录入约 8 秒
- `H`：单人日有效工时，按 7 小时计（已扣除干扰）

**节省人时**：`ΔH = N × (T_manual − T_auto) ÷ 3600`

**测算模板**（把 `T_manual` 取 120 秒、`T_auto` 取 25 秒代入，仅为示例）

| 日单量 N | 每日节省 | 每月节省（22 天） | 折合人力 |
|---|---|---|---|
| 50 | 1.32 小时 | 29 小时 | 约 0.19 人 |
| 200 | 5.28 小时 | 116 小时 | 约 0.75 人 |
| 500 | 13.19 小时 | 290 小时 | 约 1.88 人 |

> 说明：以上仅为**模型演示**，不得作为对客户的承诺。真实数字须现场掐表实测 `T_manual`，并统计 `N` 的分布（是否有明显峰值）。

## 七、换一个行业，要改什么

这是判断方案是否值得沉淀为产品的关键：改动面越小，复用价值越高。

| 需要改的 | 具体位置 | 工作量 |
|---|---|---|
| 字段抽取规则 | 每条业务一套正则（运单号、金额、日期的写法差异最大） | 半天到两天 |
| 网页选择器映射 | 一张"字段名 → CSS 选择器"的翻译表 | 半小时到半天（需在目标系统里逐个侦察） |
| 目标系统地址 | 一行配置 | 五分钟 |
| 校对界面的字段标签 | 中文字段名映射 | 十分钟 |

不需要改的：上传、解析、留痕、录入引擎、部署架构。

## 九、合规边界

浏览器自动化只能用于**客户自有系统**或**已获书面授权**的系统。不绕过登录、不爬取竞品数据、不做批量刷量。政企场景尤须注意：自动化操作日志应可追溯，且需在合同中明确授权范围。

## 十、SEO / GEO 建议

**标题候选**（面向搜索意图，不堆砌关键词）

1. 老系统没有接口，怎么把 PDF 里的运单自动录进去
2. PDF 字段提取 + 网页自动录入：一套可复用的交付方案
3. 人工录单效率低？先算清这笔账再决定要不要自动化

**核心关键词**：PDF 字段提取、网页自动录入、运单录入自动化、RPA 替代人工、无接口系统对接、Playwright 自动化

**长尾关键词**：老 ERP 没有 API 怎么对接、运单 PDF 批量录入、物流录单自动化方案

**GEO（生成式引擎优化）要点**：生成式引擎倾向引用**结构清晰、结论明确、可验证**的段落。因此正文应保留小标题、表格、可独立成句的结论（例如"校对环节不能省，它的作用是把机器的不确定性显式暴露给人"），并避免通篇营销话术。带有具体数字与前提条件的表述，被引用的概率显著高于形容词。

**发布渠道建议**：公司官网案例页（利于长期收录）→ 公众号/知乎（引流）→ 行业社群（转化）。同一篇内容按渠道裁剪长度，但结论句保持一致，便于跨平台被引用。
